# openside 확장

패치하지 않은 순정 Chromium 에 openside UX 를 제공하는 MV3 확장이다. TypeScript 로만 작성했다.

## 요구 사항

- Node 22 이상
- pnpm
- Chromium 126 이상(`sidePanel` API 와 `Promise.withResolvers` 가 필요하다)

## 설치

1. `pnpm -C extension install` 과 `pnpm -C extension build` 를 실행한다.
2. Chromium 에서 `chrome://extensions` 를 연다.
3. Developer mode 를 켠다.
4. Load unpacked 를 누르고 `extension/dist` 디렉터리를 고른다.

## 기기 연결

확장 프로그램 옵션 화면에는 발급받은 `person_device` 기기 토큰을 붙여넣어 등록한다. 운영자는 데몬 호스트에서 로컬 소켓을 통해 `openside token create --person --scope read --scope steer --scope approve`를 실행하여 토큰을 발급하며, 보안 코드·로그인·기기·원격 제어(takeover) 카드까지 처리하려면 `--scope human_step`을 추가한다. 이렇게 발급한 `person_device` 토큰은 에이전트에 절대 넘겨서는 안 된다. 토큰은 기존과 동일하게 `storage.session`에만 보관되며 브라우저를 재시작하면 페어링 정보가 초기화된다.

- 토큰은 `chrome.storage.session` 에만 둔다. local·sync 저장소에는 쓰지 않고, 로그에 남기지 않으며, 웹 페이지에 넘기지 않는다. 브라우저를 다시 시작하면 다시 연결해야 한다.
- 데몬 origin 권한은 저장할 때만 요청한다.
- 루프백이 아닌 호스트로 가는 평문 http, 사용자 정보·쿼리·프래그먼트가 붙은 URL 은 저장하지 않는다.
- 저장한 뒤에는 토큰을 다시 보여 주지 않는다.

## 기능

### Ask (사이드 패널)
- 이 탭에서 시작한 세션 목록을 보여 준다.
- 입력창은 고른 세션이나 새 세션으로 메시지를 보내고, 데몬의 답을 실시간으로 받아 보여 준다.
- 보류 중인 승인·정보 요청 카드는 패널에서 바로 답하거나 거절한다.
- 기기 승인과 직접 조작 카드는 로컬에서 작업을 마친 뒤 Done 을 누르라고 안내만 한다.
- 비밀값은 password 입력란으로만 받는다.
- 어느 대화에서 들어온 코드 요청이든 패널 안에 코드 입력 폼을 바로 띄우며, 패널이 닫혀 있을 때는 툴바 배지와 일회성 알림으로 알려준다. 알림을 클릭하면 패널이 열린다. 이 알림에 `notifications` 권한을 쓴다.
- `@` 버튼을 누르거나 `@` 만 따로 입력하면 현재 탭의 URL·제목·선택한 텍스트를 붙인다. 사용자가 직접 할 때만 동작한다.
- 어시스턴트 답변은 웹 앱(`web/src/components/Markdown.tsx`)과 동일하게 GFM 표, 목록, 복사 버튼이 포함된 코드 블록 등 Markdown으로 렌더링한다. 답변 내부의 HTML은 일반 텍스트로 표시하고, 안전하지 않은 링크 스킴은 제거하며, 이미지는 패널에서 불러오지 않고 대체 텍스트(http/https 이미지는 링크)로만 표시한다.
- 답변을 작성하는 동안에는 끝에 작게 깜빡이는 점을 표시하고, 연결 진행 상황(Connecting…/Reconnecting…)은 팝업 대신 상단 바에 작은 텍스트로 띄운다.
- 브라우저가 페어링되어 있지 않으면 오류 대신 패널에 Pair openside 버튼이 있는 페어링 안내를 표시한다.
- 카드 레이블과 버튼은 웹 앱(`web/src/components/TicketCard.tsx`) 기준을 따른다. 기본 작업 버튼은 배경을 채우고, Reject와 Dismiss는 붉은색 대신 튀지 않는 텍스트 버튼으로 둔다.

### 화면 디자인
- Ask 사이드 패널과 Options 페이지는 웹 앱(`web/DESIGN.md`)과 동일한 디자인 언어를 따른다. 밝은 테마와 어두운 테마에 맞춘 부드러운 배경 그라데이션, 알약 형태 컨트롤이 들어간 반투명 상단 바, 흰색 텍스트를 얹은 어두운 반투명 유리 카드 형태의 어시스턴트 답변, 전송 버튼이 흰색 원으로 바뀌는 반투명 알약 입력창, 로그인·코드·선택 카드 상단의 'Action needed' 칩, 아웃라인 아이콘, 토스트, 빈 화면과 오류 상태까지 모두 동일하게 적용된다.
- 확장 페이지는 런타임에 웹 스타일시트를 불러올 수 없으므로, 글래스 토큰(`--backdrop`, `--glass-strong-*`, `--pill-primary-*`, `--status-pill-*`, `--radius-glass`, `--blur-glass` 등)을 `static/style.css`에 복사해 둔다. 기준이 되는 파일은 `web/src/styles.css`이며, 여기서 토큰을 수정할 때는 `static/style.css`에 복사된 토큰도 같은 커밋에서 함께 갱신해야 한다.
- 테마는 `prefers-color-scheme` 을 따라 브라우저 설정에 맞춰진다. 확장 안에 테마 선택 기능은 없다.
- Wanted Sans 와 D2Coding(둘 다 OFL-1.1, 라이선스 전문 포함)은 빌드할 때 `web/src/assets/fonts` 에서 `dist/fonts` 로 복사한다. 확장 페이지는 외부 폰트나 스크립트를 불러오지 않고, 아이콘도 Lucide 인라인 SVG 를 쓴다.
> Ask 패널은 웹 앱과 마찬가지로 최신 메시지 아래에 전송 상태를 표시한다. 데몬이 큐에 넣으면 "Sent", 에이전트가 가져가면 "Read"가 뜨고, 에이전트가 작업 중일 때는 점 세 개로 된 입력 중 알약 모양 표시가 나타난다. 응답이 시작되면 두 상태 표시 모두 사라지며, 실패하거나 중단된 메시지에는 다음 메시지를 보낼 때까지 안내 문구(웹과 동일한 문구)가 유지된다. 작성 창과 대화 선택기의 스크롤바는 웹 UI처럼 숨겨진다.
- 패널 너비와 상관없이 가로 스크롤은 발생하지 않는다. 긴 텍스트와 URL은 메시지 안에서 줄바꿈되고, 대화 제목과 첨부 탭 레이블은 말줄임표로 자르며(마우스를 올리면 전체 텍스트 표시), 가로 스크롤은 코드 블록과 표 내부 상자에서만 동작한다.
- 상태 및 오류 메시지는 패널 입력창 바로 위와 Options 최상단에 토스트로 표시하고, 일정 시간이 지나거나 닫으면 사라진다. Options에서는 현재 브라우저의 페어링 여부와 연결된 데몬 URL을 확인할 수 있다.

### Desktop notifications
> 웹 앱의 Settings → Notifications 토글은 Web Push용 푸시 서비스가 없는 브라우저(패치된 openside 브라우저)에서 확장 프로그램이 데스크톱 알림을 보낼지를 제어한다. 이 설정을 켜면 일회용 코드(`read`, `steer`, `approve`, `human_step`)로 확장 프로그램을 페어링하고, 이전처럼 온/오프 설정을 `chrome.storage.local`에, 토큰을 `chrome.storage.session`에 저장한다. 백그라운드 워커는 `GET /v1/sessions` 및 대기 중인 티켓을 폴링하며(알람 주기 30초, 태스크 실행 중에는 5초), 실행 중이던 태스크가 끝나면 "Task finished"를, 대기 중인 새 요청이 생기면 요청당 하나씩 알림을 띄운다. 포커스된 창의 활성 탭에 열려 있는 대화는 건너뛴다. 알림을 클릭하면 해당 대화가 열리고, 요청인 경우 사이드 패널이 열린다. 매니페스트는 공개 `key`를 고정하여 확장 프로그램 ID(`jneddlbpgmlheplolfonafkbkbkjhcfj`)가 어디서나 동일하도록 보장하며, `externally_connectable`은 `http://127.0.0.1/*` 및 `http://localhost/*`만 허용한다. 확장 프로그램은 다른 데몬과의 페어링으로 교체하는 동작을 거부한다.

### Imported browser data
> 가져온 데이터는 페어링되지 않은 웹 페이지로부터 절대 수락하지 않는다. 온보딩 과정에서 `Connect the openside extension` 문구가 표시되며, 공유 커넥터를 사용해도 알림 설정은 바뀌지 않는다. 새로운 데몬 origin이 감지되면 확장 프로그램 자체 페이지가 열려 `Connect openside at <origin> for importing?`이라고 묻고, 사람이 승인해야 교환 절차가 시작된다. 기존에 기억된 origin이나 호스트 권한이 있다고 해서 동일한 앱이 여전히 해당 포트를 점유하고 있다는 증거가 되지는 않는다. 토큰이 유실된 경우, 데몬이 새로운 확장 프로그램 nonce와 교체 응답 전문을 이전 키로 서명해야만 보관 중이던 가져오기 키를 사용해 백그라운드에서 조용히 재페어링할 수 있다. 요청 헤더에 선택 사항인 `x-openside-import-device` / `x-openside-import-nonce`를 실어 이전 키를 식별하며, `x-openside-import-proof`는 `openside-import-pairing-v1\n`, 16진수 32자리 기존 기기 ID, 16진수 64자리 nonce, 응답 바이트의 원시 SHA256 해시값을 조합해 계산한 HMAC-SHA256 값이다. 이전 키가 없으면 교환 전에 확장 프로그램 자체 동의를 새로 받아야 한다. 증명 검증에 실패하면 확장 프로그램이 `openside at <origin> could not prove it's the same app you paired before`라는 경고를 띄우는 동안 교체 정보는 메모리에만 임시 유지된다. 새로 Connect 동의를 받아야 비로소 저장되며, 거부하거나 시간이 초과되면 폐기되어 이전 키가 그대로 유지된다. 토큰은 세션 스토리지에, 가져오기 키는 로컬 스토리지에 남으며, 둘 다 동의 페이지로는 전달되지 않는다.
>
> 로컬 권한이 부여된 웹 앱은 배치 ID와 정확한 쿠키 권한 origin만 확인한 뒤, 페어링된 기기와 배치에 묶인 2분 유효 1회용 티켓을 발급한다. 그리고 기존 루프백 브리지를 통해 이 티켓만 전달한다. 확장 프로그램은 저장된 데몬 origin에서 자체 기기 토큰으로 데이터를 가져오며, 고정 길이의 `ticket || batch_id || SHA256(payload)` 16진수 문자열에 대한 HMAC-SHA256을 검증하고, 이미 로컬에서 소진된 티켓은 거부한 뒤 네이티브 쓰기를 진행한다. 웹 앱은 적용이 성공했을 때만 완료 확인을 받는다. 웹 앱은 가져오기 시크릿이나 쿠키 페이로드를 일절 받지 않으며, 확장 프로그램 역시 웹 앱의 관리자 토큰이나 부트 시크릿을 일절 받지 않는다. 가져오기 시크릿 교환에는 고정된 확장 프로그램 Origin이 필요하며, 웹 origin이나 origin이 누락된 요청은 거부된다. 브라우저 외부의 로컬 프로세스는 이 헤더를 위조할 수 있지만, 해당 프로세스는 이미 신뢰할 수 있는 로컬 사람 권한 경계 내에 존재한다.

> 가져온 북마크는 `Imported from <Browser> (<Profile>)` 폴더 아래에 원래의 폴더 트리를 유지하며, 전체 폴더 경로와 URL을 기준으로 중복이 제거된다. 네이티브 방문 기록은 URL을 기준으로 중복을 제거하며, `chrome.history.addUrl`은 원래 방문 시각이 아닌 가져온 시각을 기록한다(원래 타임스탬프는 에이전트 측 보조 저장소에 보관된다). 쿠키는 host-only/domain 범위, 경로, Secure, HttpOnly, SameSite, 만료 시간, 지원되는 파티션 경계를 그대로 유지한다. 현재 소스 파서는 매핑할 수 없는 파티션은 제외한다. 만료되었거나 삭제된 쿠키는 복원되지 않으며, 전송 대기 시 쿠키 값을 평문으로 저장하지 않고 현재 에이전트 프로필의 쿠키 저장소를 직접 읽는다.

> 북마크는 `http`, `https`, `file`, `ftp` 링크를 지원한다. 브라우저 내부 링크나 실행 가능한 링크(`chrome`, `about`, `javascript`, `data` 및 기타 미지원 스킴)는 개별적으로 건너뛰고 개수만 집계하며, 지원되지 않는 북마크가 하나 있더라도 유효한 북마크, 방문 기록, 쿠키의 적용이 중단되지 않는다. 파일 및 FTP 북마크는 저장만 되며 자동으로 열리지 않는다. 방문 기록과 쿠키의 origin은 HTTP(S) 전용으로 유지된다.

> 권한 검토: `bookmarks`는 가져온 폴더 트리를 생성하고 중복을 확인하며, `history`는 방문 기록을 확인하고 누락된 URL을 추가하며, `cookies`는 가져온 쿠키를 쓴다. 광범위한 새 호스트 권한은 추가되지 않았다. 정확한 사이트 접근 권한이 없으면 쿠키는 대기 상태로 유지되며, `debugger`는 여전히 선택 사항이다. 관리되는 에이전트 프로필에는 확장 프로그램이 설치되지 않는다. 쿠키는 데몬 CDP를 통해 네이티브 방식으로 처리되며, `browser_import_lookup`은 사람이 `Allow for this conversation`을 선택한 경우에만 기본 보조 저장소에서 북마크/방문 기록을 읽어온다. `Not now`를 선택하면 해당 대화 동안 캐시된다. 이 동작은 `PrivacyRead`이므로 정책의 Deny 설정이 항상 우선한다. 주소 필드는 이 도구를 통해 절대 반환되지 않는다. 로그인용 이메일/전화번호 추천과 인식된 비보안 폼 주소 추천은 공유 글래스 콤보박스를 통해 사람에게 직접 제시되며, 자동 선택되거나 제출되지 않는다. 비밀번호, 이메일/사용자명/OTP, 결제 정보 및 알 수 없는 폼 필드에는 아무런 추천도 제공되지 않는다.

> 가져온 사이트에 접근 권한이 필요하면 온보딩에서 `Sign in to your sites in openside` 항목을 안내한다. 인증된 티켓이 있으면 확장 프로그램이 가져온 정확한 호스트 목록을 직접 도출한 뒤, `Allow` 버튼 하나가 있는 자체 페이지를 연다. 이 버튼을 클릭하면 기존 선택적 권한 중에서 해당 호스트 권한만 요청하며, 모든 사이트에 대한 전체 권한을 요청하거나 매니페스트에 추가하지 않는다. 웹 앱은 권한 부여를 감지하여 전송 티켓을 재발급하고 진행 상황과 결과를 표시한다. 공개 호스트 쿠키는 원래의 `Secure` 플래그를 변경하지 않고 HTTPS 설정 URL을 사용한다. 창을 닫거나 거부하더라도 가져온 데이터는 그대로 저장되어 나중에 다시 시도할 수 있다.

> 가져온 쿠키는 에이전트 브라우저 내에서 로그인하여 생성된 쿠키와 동일한 신뢰 경계를 가진다. 권한이 부여된 사이트에서 실행되는 스크립트는 해당 사이트의 non-HttpOnly 쿠키를 읽을 수 있다. 가져온 쿠키 값은 전역 텍스트 마스킹 패턴으로 등록되지 않는데, 일반 설정값까지 일괄 등록하면 무관한 페이지 텍스트까지 가려지기 때문이다. 가져오기 전송 과정에서는 작업, 이벤트, 대기 파일에 쿠키 값을 일절 포함하지 않는다. Vault 비밀번호는 기존의 마스킹 및 암호화 저장소 보호 체계를 그대로 유지한다.

> 확장 프로그램의 전송 조회는 전역 `Storage.getCookies`가 아니라 `Network.getCookies`를 사용하여 현재 배치의 호스트/경로 URL로 범위가 한정된다. Chromium이 해당 URL에 일치하는 다른 쿠키를 반환할 수도 있지만, 정확한 호스트/이름/경로 키로 즉시 필터링된다. ConnCore가 추가한 별도의 Connections 인벤토리는 현재 네이티브 가져오기 이후 프로필 전체를 대상으로 `Storage.getCookies` 메타데이터 스캔을 실행한다. 이 파서는 값 문자열을 즉시 영구 삭제(zeroize)하며 쿠키 값을 보관하거나 노출하지 않지만, 전체 응답이 해당 과정에서 일시적으로 버퍼링된다. 데몬이 소유한 파싱된 JSON 값, 쿠키 DTO 값, 원시 페어링 키, 서명된 페이로드 문자열은 메모리 해제(drop) 시 영구 삭제되며, 확장 프로그램의 바이트 버퍼는 덮어쓰고 시크릿 참조는 해제된다. 완전한 소거가 보장되는 것은 아니다. 불변 JS 문자열, Chrome 스토리지/네이티브 API 버퍼, HTTP 바디, WebSocket 프레임, 암호화 라이브러리 내부 메모리 등에는 자체 폐기 전까지 사본이 남아 있을 수 있다. 이러한 한계가 있더라도 앞서 언급한 브라우저 쿠키의 신뢰 경계는 달라지지 않는다.

> 에이전트의 일반 파일 도구로는 심볼릭 링크나 상위 디렉터리 별칭을 포함하여 `<data>/browser-imports` 아래의 레코드나 `<data>/extension-import-keys` 아래의 키를 읽거나 조회할 수 없다. 샌드박스 처리된 bash에서는 해당 비공개 트리가 빈 tmpfs 마운트로 표시되며 셸 글로브를 통해서도 접근할 수 없다. 정책 설정으로 명시적 활성화된 비샌드박스 셸은 격리 경계가 아니므로 OS 사용자 권한으로 파일에 접근할 수 있다. 가져오기 프라이버시 권한은 이러한 안전하지 않은 모드나 데몬의 다른 비공개 디렉터리까지 보호한다고 보장하지 않는다.

### Omnibox
주소창에 `os`, 공백, 질문을 차례로 입력하고 Enter 를 누르면 새 세션을 시작하고 Ask 를 연다.

### Gmail·Slack 웹
"Handle with openside" 버튼이나 컨텍스트 메뉴를 쓰면 메시지 안에서 선택한 텍스트(또는 열린 메시지 본문)와 출처 URL 을 새 세션으로 넘긴다. 자동으로 보내는 것은 없다. 페이지 내용은 지시가 아니라 인용한, 신뢰할 수 없는 맥락으로 전달한다.

버튼은 닫힌 shadow root 안에 있어 실제 사용자가 클릭했을 때만 반응한다. 웹페이지 스크립트가 `.click()`을 호출하거나 가짜 이벤트를 발생시켜도 아무런 동작도 일어나지 않는다. 컨텍스트 메뉴 동작은 브라우저가 사용자 입력을 바탕으로 생성하며, 현재 탭의 URL과 일치하는 최상위 Gmail/Slack 문서에서 보낸 요청만 받아들인다. SPA 특성상 URL 해시(#)는 바뀔 수 있지만, origin·path·query는 반드시 일치해야 한다.

### Agent Tabs
- 프로덕션 빌드에서 `debugger` 권한은 선택 사항이다. Options 화면에서 `Enable Agent Tabs`를 누르면 Chrome의 `debugger` 권한을 요청하고(타깃 메타데이터를 읽는 용도로만 사용) 이번 브라우저 세션에 한해 탭 그룹 기능을 켠다. `Disable Agent Tabs`를 누르면 확장 프로그램이 만든 탭 그룹을 모두 해제한다.
- Ask, 메시지 처리, 페어링은 이 권한 없이도 동작한다.
- 확장 프로그램은 주기적으로 `GET /v1/browser/tabs`를 호출해 데몬의 탭 ID를 `chrome.debugger.getTargets` 결과와 대조한다. URL 일치 여부로 탭을 묶지 않으며, 디버거를 연결하거나 브라우저를 직접 제어하지도 않는다.
- 에이전트가 이 브라우저에서 직접 연 탭만 그룹으로 묶인다. 비공개 세션의 탭은 데몬이 목록에서 제외한다.
- 에이전트 탭을 묶으려면 `browser.extensions` 설정에 `extension/dist` 경로를 지정해 데몬이 실행하는 브라우저에 이 확장 프로그램을 올려야 한다. 사용자가 따로 띄운 브라우저에서는 데몬의 탭을 묶을 수 없다.
- `browser.extensions`는 Chromium이나 Chrome for Testing에서 동작한다. Google Chrome 정식 버전은 137부터 명령줄 인수인 `--load-extension` 옵션을 제거했다. 사용자가 직접 연 브라우저의 `chrome://extensions`에서 압축 해제된 확장 프로그램을 로드할 수는 있지만, 이 브라우저로는 데몬 소유의 탭을 묶을 수 없다. 설정된 실행 파일이 Google 브랜드 Chrome으로 보이면 `openside doctor`가 경고를 띄운다.
> Agent Tabs 그룹의 이름은 "Agent Tabs"이며 색상은 회색(Chromium의 고정 팔레트 중 가장 눈에 띄지 않는 칩)이다. 그룹 이름과 색상은 확장 프로그램이 그룹을 처음 생성할 때만 적용되므로, 사람이 이름을 바꾸거나 색상을 변경하거나 그룹을 접더라도 주기적인 동기화 중에 유지된다. 패치된 브라우저의 자체 게이트웨이(`chrome/browser/openside/agent_gateway.cc`)도 같은 이름으로 그룹을 생성하지만, 해당 패치를 수정하고 브라우저를 다시 빌드하기 전까지는 파란색으로 유지된다.

## 비밀번호 관리자

`openside doctor`는 표준 NativeMessagingHosts 디렉터리를 훑어 1Password나 Bitwarden 같은 알려진 호스트 매니페스트 파일이 있는지 확인한다. 이때 데몬 관리 프로필 디렉터리인 `<data_dir>/browser-profile/NativeMessagingHosts`도 함께 점검한다. 일반 사용자 브라우저 디렉터리에 매니페스트가 있다고 해서 해당 관리 프로필에서도 연동이 동작한다는 뜻은 아니다. Linux에서는 Flatpak 브라우저 경로와 Snap Chromium 공용 프로필 경로도 확인하며, 샌드박스 패키지는 패키지별 추가 설정이 필요할 수 있다. 매니페스트 파일이 존재한다고 해서 네이티브 호스트가 실제로 실행되거나 벤더 연결이 정상 동작한다고 단정할 수는 없다. doctor 명령은 매니페스트 내용을 읽거나, 파일을 복사·링크하거나, 호스트 프로그램을 실행하거나, 기존 연동 설정을 변경하지 않는다.

`tools/pwmgr-qa.sh all` 로 openside 와 비밀번호 관리자 확장을 함께 띄우는 검증을 재현한다(단계는 `tools/pwmgr-qa/run.mjs`).

**Bitwarden**: 스토어 빌드(확장 2026.9.3)를 로컬 Vaultwarden 서버에 연결해 순정 Chromium 152 와 패치 빌드에서 확인했다.
- 데몬이 띄운 브라우저(`browser.extensions`)에 openside 확장과 함께 로드되고 두 서비스 워커가 모두 동작한다.
- 에이전트 탭의 로그인 폼은 비어 있고 Bitwarden 이 임의로 채우지 않는다. 탭 원장에는 에이전트 탭만 나온다.
- openside 는 비밀번호 관리자 데이터를 읽지 않는다. 소스 정적 검사와, Bitwarden 잠금 해제·자동완성 뒤 openside 데이터 트리 검사에서 마스터 비밀번호와 항목 비밀번호가 나오지 않았다.
- 데몬이 관리하는 헤드리스 패치 브라우저에서 Bitwarden 로그인이 된다. 사용자 탭 자동완성과 폼 제출은 창을 띄운(headed) 순정 Chromium 개발 실행에서 확인했다. 순정 헤드리스 Chromium 은 Bitwarden 팝업을 그리지 못하지만 openside 때문은 아니다.

주의할 점:
- 비밀번호 관리자가 채운 사용자명·이메일 같은 필드는 일반 페이지 상태다. 자동완성이 에이전트 탭에 들어가면 에이전트가 REPL 로 읽을 수 있고 이벤트 로그에 남을 수 있다. 비밀번호 입력란은 Chromium 이 가려서 읽히지 않았다.
- `--user-data-dir` 를 준 Chromium 은 `<data_dir>/browser-profile/NativeMessagingHosts` 만 읽는다. Bitwarden 데스크톱 호스트 매니페스트를 그 디렉터리로 복사해야 한다(doctor 도 같은 안내를 한다).
- 알려진 문제: 데몬이 브라우저를 띄울 때 `XDG_CACHE_HOME`·`XDG_DATA_HOME` 을 프로필 안의 디렉터리로 바꾼다. Bitwarden `desktop_proxy` 는 데스크톱 앱 소켓을 `$XDG_CACHE_HOME/com.bitwarden.desktop/s.bw` 에서 찾으므로, 데몬이 관리하는 브라우저에서 Bitwarden 데스크톱 앱으로의 연결은 아직 되지 않는다(재현: `tools/pwmgr-qa.sh up && STAGES=native tools/pwmgr-qa.sh run`). 실제 데스크톱 앱과의 전체 핸드셰이크는 실행하지 않았다.

**1Password**: 설치와 로드까지만 확인했다(확장 8.12.41.1 이 openside 확장과 함께 로드되고 서비스 워커가 둘 다 동작하며, 설치 직후 자체 온보딩 페이지를 연다). 로그인, 자동완성, 데스크톱 앱 연동은 유료 계정과 데스크톱 앱이 필요해 `blocked-external` 이다.

사용자 할 일: 일회용 브라우저 프로필에 1Password 확장과 데스크톱 앱을 본인 계정으로 설치하고, 제품 안내에 따라 네이티브 연결이 되는지 확인한다.

## 테스트

```bash
pnpm -C extension lint
pnpm -C extension typecheck
pnpm -C extension test
pnpm -C extension build
cargo test -j 8 -p openside-e2e --test extension
```

- 배포 빌드의 콘텐츠 스크립트는 `https://mail.google.com/*`, `https://app.slack.com/*`, `https://*.slack.com/*` 에만 붙는다.
- 플래그 없이 빌드하면 이름이 `openside`로 지정되고 실제 호스트에만 매칭된다. `debugger` 권한은 선택 사항으로 남으며 루프백 호스트 권한도 포함되지 않는다. `OPENSIDE_EXTENSION_TEST_MATCHES=1`로 빌드하면 이름이 `openside (test build)`로 바뀌고, `http://127.0.0.1/*` 및 테스트 픽스처 경로인 `/gmail`, `/slack` 매칭이 추가된다. 이 빌드는 일회용 테스트 프로필에서만 쓰이며 `debugger` 권한과 루프백 접근 권한을 처음부터 부여받는다.
- E2E 테스트는 임시 디렉터리(`OPENSIDE_EXTENSION_OUTDIR`)에 있는 테스트 빌드를 `browser.extensions`로 가리키는 실제 테스트 데몬을 띄운다. 데몬은 독립된 임시 프로필 환경에서 stock Chromium을 `--headless=new` 옵션으로 실행한다. 이 테스트는 마지막 메시지뿐 아니라 이전에 선택한 Gmail 및 Slack 메시지가 출처 URL과 함께 전달되는지, 실제 CDP 마우스 클릭만 처리하고 웹페이지의 가짜 클릭은 무시하는지, Ask 응답이 스트리밍되는지, 정확한 ID로만 탭을 묶고 동일한 URL을 띄운 일반 사용자 탭은 묶지 않는지 검증한다.
- E2E 테스트에서는 200자 URL과 공백 없는 긴 한국어 텍스트가 주어졌을 때 320·400·480px 너비의 패널과 320px 너비의 Options 페이지에서 가로 스크롤이 생기지 않는지 검증한다.
- 헤드리스 환경에서는 Chrome의 권한 확인 팝업을 클릭할 수 없으므로 E2E 테스트에서 이 과정을 다루지 않는다. 대신 실제 Options 페어링 절차와 `Enable Agent Tabs` 버튼 동작은 그대로 검증한다.
- 테스트 빌드는 평소 쓰는 프로필에 설치하지 않는다.
